### <a name="_qmphm5d6rvi3"></a>**Решение**  
Для обеспечения масштабируемости, отказоустойчивости и быстрого отклика предлагается Event-Driven микросервисная архитектура:


1. **Kafka**  
   - Шина событий для всех заявок и подтверждений  
2. **Deposits Service** (.NET Core)  
   - Читает события из Kafka, адаптирует payload под API АБС  
3**АБС** (Oracle/Delphi)  
   - Хранение ставок, создание депозитных счетов, управление рисками  
4**SMS-шлюз**  
   - Внешняя интеграция с телеком-оператором через HTTP API  
5**Сайт** (PHP/React.js) и **Интернет-банк** (ASP.NET MVC)  и сервис парсинга ставок(PHP)
   - UI и базовая бизнес-логика для подачи заявок  
6**Мониторинг и логирование**  
   - Prometheus/Grafana для метрик, ELK для логов


#### Обоснование выбора  
- **Асинхронность** через Kafka разгружает АБС и повышает устойчивость при нагрузке.  
- **Микросервисы** позволяют разворачивать и масштабировать депозиты независимо от монолитов.  
- **Повторное использование** существующих СУБД и технологий ускоряет внедрение и снижает риски.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**  
1. **Синхронные REST-вызовы** напрямую из интернет-банка в АБС  
   - + Минимум новых компонентов  
   - – Перегрузка АБС, низкая отказоустойчивость  
2. **RabbitMQ вместо Kafka**  
   - + Проще в настройке  
   - – Меньшая производительность при масштабировании  
3. **Расширение существующего монолита интернет-банка**  
   - + Нет микросервисов  
   - – Ограниченная масштабируемость, сложность поддержки  

---

### **Недостатки, ограничения и риски**  
- **Нагрузка на АБС**: пики сообщений могут привести к деградации производительности БД.  
- **Сложность эксплуатации Kafka**: требуется кластеризация, репликация и обучение команды.  
- **Безопасность**: необходим аудит конфигураций TLS и соответствие 152-ФЗ.  
- **Операционные риски**: отказ депозитного сервиса приведёт к задержкам в обслуживании клиентов.
